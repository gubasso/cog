# Open questions

Every entry names what it blocks and exits through an ADR, a slice revision, or a recorded measurement.

## Q-005 — Does `gc` belong in the curated terminal-contract map?

Blocks: nothing today; `terminal-contract` is opt-in, so leaving `gc` out fails nothing. Raised: the gc leanup, which gave `gc` its own inline commit path emitting `COMMIT_OK <sha>` directly rather than only aggregating a worker's line — the same shape the rule curates for `gc-repo`. Exit: an ADR or a recorded decision to add `gc` to the map in `lib/commands/cmd_skill_lint.sh`, `docs/reference/skill-contract.md`, and the `cmd_skill_lint.bats` fixtures, or to keep the map scoped to fresh-context workers only.

## Q-007 — How does a Codex host reach Claude for cross-engine work?

Blocks: the Codex `executor-oneshot`'s `good-input` route, which exists to have the opposite engine review a plan and currently reviews on its own engine instead, so the independence it exists for is unavailable. Raised: the single-executor leanup, which found that route instructing a Codex session to delegate "through the Task/Agent tool" — a Claude-side tool a Codex host does not have. `cog codex-runner` runs Claude-to-Codex only; there is no lane the other way. Exit: slice 006 [provider-runners](./slices/006-provider-runners/README.md), which adds `claude-runner` beside `codex-runner` and is itself governed by slice 005 [orchestrator-conformance](./slices/005-orchestrator-conformance/README.md) — so the vendor-neutral runner contract lands first, then both runners against it. While the degrade stands, `cog executor prepare-step --executor executor-oneshot --engine codex --route good-input` resolves `prepare_engine: claude`, and `cog executor summary` copies that into `executor-summary.json` — correct for the Claude-hosted `executor-oneshot-codex` twin, which really does review in Claude, and wrong for the Codex-hosted `executor-oneshot` twin, which now reviews in session on Codex. Both twins pass `--engine codex`, so the `(executor, engine, route)` key cannot separate them: the engine names who executes, not who hosts. Correcting the record therefore needs the caller to supply the engine that actually prepared, since only the twin knows its own host. The divergence is named in `docs/reference/cli-commands.md` and in the skill so no auditor reads it as a real cross-engine review. When that lane exists, restore the route to a real cross-engine call, drop the interim degrade the skill records, and this note with it.

Q-006 asked whether `cog executor prepare-step` should gain an `inline` lane and a host dimension, or whether lane ownership should leave the CLI. It exited the second way: `prepare-step` no longer reports a lane (`cog.executor.prepare-step.v2`), because the same producer runs inline on one host and forked on another, and a fork chosen for bias isolation rather than engine mismatch is judgment no lookup key can express. The rule now lives in prose as the inline-by-default pattern in `skill-refs/orchestration/orchestration-patterns.md`.
