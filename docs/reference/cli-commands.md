# CLI commands

`cog` is machine-facing. `--json`, generated help, man pages, Bash completion, `doctor`, and `init` are self-documentation and setup surfaces for agents and scripts. `init` initializes cog's runtime directories and prerequisites.

## Global flags

`cog` accepts these global flags before the command name:

| Flag                | Meaning                                             |
| ------------------- | --------------------------------------------------- |
| `-h`, `--help`      | Show help.                                          |
| `-V`, `--version`   | Show version.                                       |
| `--json`            | Request JSON when a command has a non-JSON default. |
| `--dry-run`         | Show what would happen without changing state.      |
| `--print-config`    | Print resolved configuration and sources.           |
| `-v`, `-vv`, `-vvv` | Increase verbosity.                                 |

## Command discovery

Command modules live in `lib/commands/cmd_*.sh`. The loader maps a dash-form command name to an underscore-form module and handler:

```text
cog print-config -> lib/commands/cmd_print_config.sh -> cog::cmd::print_config
```

The line-2 `: 'desc: ...'` sentinel in each command module is the summary source for root help and this reference table.

## Mirrors

Root help is generated dynamically by `lib/functions/fn_help_generate.sh`. `completions/cog.bash` and `man/cog.1.scd` are machine self-documentation mirrors of the command surface and must be kept in sync with `lib/commands/cmd_*.sh`.

## Plan reviews and folded plans

`cog plan-review items <review-abs.md> [--json]` scans only the exact `APPROVED`, `MODIFIED`, `REMOVED`, and `ADDED` sections under `## Annotated Plan`. It emits `schema: "cog.plan-review.items.v1"`, `action: "items"`, `ok`, absolute `path`, `count`, and `items[]`. Each item has `{id, annotation, ordinal, start_line, end_line, markdown}`. IDs are derived by annotation and one-based source ordinal (`A1`, `M1`, `R1`, `D1`); authors do not write them. Top-level Markdown list entries are canonical, with level-four headings and paragraph blocks supported for older reviews.

`cog plan-review fold-check --review <review-abs.md> --plan <plan-abs.md> --manifest <manifest-abs.json> [--json]` accepts a manifest with exactly `schema: "cog.plan-review.fold-manifest.v1"` and `dispositions[]`. Each disposition has an `id` and a `disposition` of `folded` or `waived`; waived items require a non-blank `reason`, and folded items may have a `note`. Duplicate, unknown, missing, malformed, invalid, or unreasoned dispositions fail closed with `$EX_DATAERR` in JSON mode. An empty manifest is valid only for a zero-item review.

The result uses `schema: "cog.plan-review.fold-check.v1"`, `action: "fold-check"`, and contains `ok`, the three absolute paths, `review_sha256`, `plan_sha256`, `manifest_sha256`, `{total, folded, waived}` counts, and structured `errors[]`. It proves deterministic coverage, not semantic correctness. A retained receipt is current only while all three hashes still match the files it names, so any later edit to the review, the plan, or the manifest makes it stale until validation and fold-check are rerun. A manifest that is not exactly one top-level JSON value — a syntax error or a multi-document stream — is reported as a structured `invalid_manifest` error, not a parse failure.

`cog review-plan-multi-setup [--json] [--solo] [--output <absolute.md>] <input>` returns the caller override as `FINAL_REVIEW`; without it, the default remains the run-directory `final-review.md`.

`cog preflight claude <out.json>` reports the Claude wrapper's launch preconditions — binary on `PATH`, a version it will report, and a bound account — as `claude_session.{available,health,version,auth}`. `cog preflight codex <out.json>` is its Codex counterpart, reporting `codex_session.{available,health,auth}`. Both are what `run-exec` runs before it creates a durable state file, per [ADR-0031](../decisions/ADR-0031-preflight-provider-preconditions-before-the-durable-job.md). `auth` is a separate reading from `health`, because a wrapper that reports a version but has no bound account still cannot launch. `cog preflight sandbox <out.json>` reports sandbox capability rather than credentials and publishes no `auth` field.

`cog preflight claude-env <out.json>` asserts the Claude Code no-backgrounding session env. Strict mode requires `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`; Bash timeout env vars are recorded as diagnostics only.

`cog codex-runner orientation <read-only|write>` prints the canonical Codex prompt orientation block for the requested access mode.

`cog codex-runner explain-status <status>` explains a status returned by `cog codex-runner` classification. Those statuses are provider diagnostics rather than a second classification; a caller branches on the exit code.

`cog executor init` creates a shared executor run directory for one prompt or plan. Its identity flags are split by responsibility:

```bash
cog executor init --executor <executor-vetted|executor-oneshot|plan-vetted> --engine <claude|codex> --input <prompt-or-plan> [--json]
```

`--executor` selects the executor skill/routine and flow; `--engine` selects the coding agent. The removed `--plan-engine` flag is not accepted. The executor flows share the gated 2-phase shape (`prepare`, `execution`): the prepare stage produces or reviews the plan depending on the input-quality route, then the plan is executed. `executor-vetted` is Claude-only (`--engine codex` is rejected); it delegates the whole prepare stage to `/plan-vetted`. `executor-oneshot` runs on either engine; its prepare producers are `/plan-oneshot` (generate) and `/review-plan-oneshot` (review, resolved to the opposite engine for independence). The `plan-vetted` flow is a Claude-only, single prepare phase (no execution): its producers are the dual-engine `/plan-multi` (generate) and `/review-plan-multi` (review). Input classification (`.md` path vs. prompt) is a hint only; the route comes from the `assess-input` verdict.

`cog executor classify-input <input> --json` reports whether the input is a readable `.md` plan or a prompt. `cog executor prepare-step --executor <e> --engine <eng> --route <needs-plan|good-input>
--json` resolves the prepare-stage producer skill, the engine the flow assigns it, and the prepare artifact, emitting `schema: "cog.executor.prepare-step.v2"`. `prepare_engine` is the flow assignment, not an observation; a caller can declare its host with `cog executor summary --prepare-engine`. Invocation-lane judgment remains in skill prose. `cog executor adopt-prepared --run-dir <dir> --from <path> --json` copies only a structurally valid plan-doc into canonical `prepared-plan.md`; an annotated `review-plan-multi` output must be retained and folded by its consumer first. `cog executor adopt --run-dir <dir> --ordinal <ordinal> --from <path> --json` similarly requires a plan-doc for `prepare`, while execution reports retain their non-empty contract. `cog executor verify-artifact --run-dir <dir> --ordinal <ordinal> --json` applies the same plan-doc requirement to the canonical prepare file and the non-empty requirement elsewhere. `cog executor export-prepared --run-dir <dir> --output <path> --json` validates canonical `prepared-plan.md` before export. cog owns canonical artifact names and their postcondition gates (see [ADR-0010](../decisions/ADR-0010-executor-preparation-and-artifacts.md)).

`cog executor artifacts <run-dir> --json` emits `schema: "cog.executor.artifacts.v2"` with a phase-keyed `phases[]` array. Each phase includes `ordinal`, `phase`, `artifact`, and `path`.

`cog executor summary` writes `executor-summary.json` and emits `schema: "cog.executor.summary.v3"`:

```bash
cog executor summary --run-dir <dir> --executor <executor-vetted|executor-oneshot> --engine <claude|codex> --route <needs-plan|good-input> --prepare <done|failed> --execution <done|failed> [--prepare-engine <claude|codex>] [--json]
```

The summary records the route, the resolved producer, and the prepare/execute engines. `--prepare-engine` declares the engine that actually prepared and wins over the flow-table assignment; omit it to record what the flow is designed for.

`cog assess-input` owns the deterministic side of the executor input-evaluation gate: `facts
[--input-file <p>] [--file <p> ...] --json` extracts structural plan-quality signals; `record
--run-dir <dir> --route <needs-plan|good-input> --confidence <high|medium|low> --rationale <text>
[--signal <k=v> ...] --json` persists and validates the verdict (`schema:
"cog.assess-input.v1"`); `validate <path>` checks an existing verdict. The judgment itself lives in the `assess-input` skill.

`cog skill-refs root` prints the resolved skill-reference root, preferring the XDG install location and falling back to the repo checkout.

`cog skill-refs path <rel>` prints an existing file under the resolved skill-reference root.

`cog skill-refs inspect [--json]` reports the resolved root together with its `origin` (`repo` or installed `xdg`), `writable`, and a `vcs_note`, so a caller can see whether a template write lands in the tracked repo or the installed, uncommitted tree.

`cog bootstrap-audit --json` reports, per domain, the machine-explicit scope fields `default_in_scope`, `default_action` (`install` when the domain is absent, `reconcile` when present), and `requirements_satisfied` alongside the existing `present`/`requirements[]` layers. The orchestrator reads `default_action` rather than re-deriving scope (ADR-0019).

`cog bootstrap-template-review check|stamp` is the freshness-cached template-review surface the `bootstrap-*` workers share. `check` selects a fresh research-shelf entry for a domain and detected type (the freshness key is `bootstrap-template,<domain>,<type>`) by comparing today against the stamped `revalidate-after`, and folds in the skill-refs origin and template roots; `stamp` records a dated review through `cog research-shelf record`, sets `revalidate-after` to the recorded date plus its `--freshness-days` window (default 14), and fails fast when the skill-refs template SoT is not writable. The freshness window is chosen at stamp time, so `check` only compares dates. Freshness selection lives here, not in `research-shelf`.
